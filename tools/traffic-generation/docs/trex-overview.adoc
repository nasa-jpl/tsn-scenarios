= TRex Overview

== What It Is

Open-source stateless packet generator from Cisco. Generates crafted Ethernet frames at high rates with per-packet control over headers, timing, and payload content. Requires a pair of NICs (TX and RX).

In our setup, TRex runs on ngasrv0 with two 10G NICs connected to the switch. Traffic loops back through the switch to the RX NIC. Currently using AF_PACKET mode (kernel sockets), not native DPDK — see link:dpdk-investigation.adoc[dpdk-investigation.adoc] for why.

== What It Enables

* Full control over every header field (MAC, VLAN, PCP, IP, UDP) via Scapy packet construction
* Precise rate control: continuous (exact pps) or burst (N packets at a rate, then pause)
* Multiple independent streams on one port, each with different priority/rate/burst pattern
* Live rate changes without stopping traffic

== The STL API

TRex's Stateless (STL) API is the Python library we use to define traffic profiles and interact with the generator. It provides primitives for packet construction, stream modes, measurement, and per-packet modification.

Full docs: https://trex-tgn.cisco.com/trex/doc/cp_stl_docs/index.html

== Traffic Profiles

The goal is to define a traffic profile (a Python class) that tells TRex what packets to send and how to send them.

TRex loads a Python file as a module. It expects a `register()` function that returns an object with a `get_streams(direction, **kwargs)` method. That's the entire interface.

[source,python]
----
def register():
    return MyProfile()
----

`get_streams()` returns a list of `STLStream` objects. Each stream has:

* A *packet* — built with Scapy (Ether/VLAN/IP/UDP layers)
* A *mode* — how to send it (continuous or burst)
* Optional *flow stats* — for measurement (see below)

Start a profile: `start -f <profile.py> -p 1 --force`

Pass kwargs: `start -f <profile.py> -p 1 --force -t pps=50000,burst_pkts=100`

=== Stream Modes

[cols="1,2"]
|===
| Traffic Type | STL Mode

| Continuous
| `STLTXCont(pps=N)` — fixed rate, runs until stopped

| Periodic burst
| `STLTXSingleBurst(pps=N, total_pkts=M)` + stream chaining (see below)

| Variable rate
| `STLTXCont` + live `update` command to change pps at runtime

| Mixed priority
| Multiple streams on same port with different PCP values in the VLAN tag
|===

=== Stream Chaining (Burst Patterns)

For periodic bursts, two streams form a loop:

1. *burst* (`self_start=True`) — sends N packets at a given pps, then triggers the pause stream via `next=`
2. *pause* (`self_start=False`) — waits for `isg` microseconds, sends 1 dummy packet, triggers burst again

Multiple queues are phase-offset using `isg` on their initial burst stream (e.g., Q3 starts 500μs after Q2).

=== Our Profiles

* `tsn_profile_tas.py` — three continuous streams (Q2, Q3, Q7)
* `tsn_profile_tas_burst.py` — Q2/Q3 as TAS-aligned bursts, Q7 continuous

== Measuring Latency

=== The easy way: STLFlowLatencyStats

Attach `STLFlowLatencyStats(pg_id=N)` to a stream and TRex handles everything — it embeds a 16-byte trailer in each packet (magic byte, sequence number, TX timestamp) and calculates latency on the RX side automatically.

This is software-timestamped (~μs precision), which is fine for seeing the broad effect of TAS gating but not sufficient for ns-level accuracy.

*Limitation:* `STLFlowLatencyStats` cannot be used on chained burst streams. TRex throws "non-sequenced stream pointing to sequenced stream" if you try. `STLFlowStats` (counter-only, no latency) works on chained streams, but it just counts packets — no per-packet latency.

=== Hardware timestamps: network taps

For ns-precision latency, we use external ProfiShark taps with GPS-synced clocks (see link:network-tap.adoc[network-tap.adoc]). One tap on the ingress link, one on the egress link. Each tap timestamps every packet independently of the system under test.

The dashboard captures pcapng from two tshark processes (one per tap), parses the packets, and matches ingress to egress by a unique packet ID to compute latency.

For continuous streams, the `STLFlowLatencyStats` trailer already contains a unique sequence number — the tap parser reads that directly.

=== The problem with bursts + taps

For burst streams, we can't use `STLFlowLatencyStats` (chaining limitation above), so there's no trailer to match on. We need another way to give each packet a unique ID.

TRex has a *field engine* — a per-packet VM that can modify any byte in the packet before transmission. We use it to inject a random 64-bit ID into the UDP payload of every packet:

[source,python]
----
STLVmFlowVar(name="pkt_id", size=8, op="random", ...)   # generate random 64-bit value
STLVmWrFlowVar(fv_name="pkt_id", pkt_offset=46)         # write at UDP payload start
STLVmFixChecksumHw(l3_offset=18, l4_offset=38, ...)      # recalc checksums in hardware
----

The payload offset (46) is: Ether(14) + VLAN(4) + IP(20) + UDP(8) = 46 bytes to the start of UDP payload.

Why `op="random"` and not `op="inc"`? An incrementing counter resets to `min_value` every time the burst→pause→burst chain restarts, causing duplicate IDs and breaking the match logic. Random 64-bit values have negligible collision probability.

The tap parser tries the `STLFlowLatencyStats` trailer first, then falls back to reading the 8-byte field engine ID. This lets both continuous and burst streams coexist.

== Known Limitations

* *Requires port pairs.* Must define an even number of interfaces — always a TX/RX pair.
* *AF_PACKET caps throughput.* CPU becomes the bottleneck before line rate. At ~500k pps total we start hitting limits.
* *Burst timing is free-running.* ISG-based burst cycles are not phase-locked to the switch's TAS gate schedule. Bursts drift relative to the gate windows over time.
